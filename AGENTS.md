# AGENTS.md

Agent Runner starts local commands and controls their process groups. The
ReAct example uses Pydantic AI and an existing inference server.

Apply these project conventions from Orla, Braid, Shared Cache World Model,
and Éire Society.

## Writing

- Write in the active voice. Use concise, clear, complete sentences that
  make sense on their own. Name the actor and action. Define a term where
  it first appears if the reader needs the definition.
- Use plain language. Avoid mannered prose, punchy fragments, slogans,
  and vague openings. Say what the code does and state limits directly.
- Use periods and commas. Avoid em dashes, en dashes, semicolons, and
  unnecessary parentheses in prose.
- Use headings that name the subject. Keep related material together.
  Cut filler, redundant headings, and introductions that repeat headings.
- Put every command the reader should copy in a fenced code block with
  its language. Give each independent action its own block. Use one block
  for multiple lines only when the lines form one command or must run
  together. Do not put runnable commands or snippets in inline code.
- Explain what each command does before its block. Explain meaningful
  flags and placeholders. Show output only when it helps the reader
  interpret the result, and put that output in a separate block.
- Use tables for related settings and defaults. Keep prose, comments,
  commit messages, and docs free of emoji and ASCII diagrams.
- Explain an invariant or surprising constraint in a comment when the
  code cannot. Use complete sentences and keep comments short.

## Python

- Use uv for the project environment and lockfile, Ruff for formatting
  and lint, ty for type checks, and pytest for tests. Pin direct
  dependencies and commit the lockfile generated by uv.
- Keep runnable examples under examples/. Declare each standalone script's
  dependencies in its uv script metadata and commit its lockfile.
- Put runner dependencies in project dependencies and development tools
  in the dev dependency group.
- Type every function signature. Use built-in generic types and union
  syntax. Use dataclasses or Pydantic models for data crossing a boundary
  when that structure helps callers.
- Keep imports at module scope. Allow a local import for an optional
  dependency or an unavoidable cycle and explain the reason.
- Use descriptive names. Name intermediate results when they explain
  the operation. Keep error handling narrow and preserve the cause when
  wrapping an exception.
- Reuse the standard library or a maintained package when it reduces
  implementation and maintenance work. Add services, configuration, or
  abstractions only when a concrete requirement calls for them.

## Commands and tests

- Use just for setup, recurring operations, and the development gate.
  Keep the run, fmt, lint, typecheck, and check recipes.
- Test observable behavior. Use real child processes for lifecycle
  tests and a small fake HTTP server when a test needs a network boundary.
  Add tests that catch distinct failures.
- Run the development gate before committing.

just check
